# 预算锁 Encumber

**Agent 团队的链上项目预算：Agent 锁款后，供应商凭链上承诺就敢开工；Agent 掉线、财务想挪钱，都动不了这笔承诺，账始终对得上。**

## 一、我们解决什么问题

越来越多公司让 AI Agent **自己花钱**：调大模型、买数据、租算力。一个团队往往同时跑好几个项目，每个项目挂几个 Agent，财务还会在项目之间调拨预算。

这时会出三个问题：

1. **供应商不敢开工**：按量计费的服务事先不知道要花多少。Agent 下了单，供应商却不确定事后能不能收到钱：Agent 可能掉线，财务可能把预算挪走。
2. **同一笔钱被承诺两次**：财务正把甲项目剩下的钱调给乙，甲的 Agent 同时在花这笔钱。两边都以为钱是自己的，结果超支。
3. **月底才发现账对不上**：传统做法靠事后对账，发现问题时钱早就花出去了。

一句话：**多个 Agent 和财务同时动同一份预算，没有人能保证“这笔钱只被承诺一次”。**

## 二、我们怎么解决

合约把每个项目的预算拆成三种状态，实时维护：

| 状态       | 含义                                           |
| ---------- | ---------------------------------------------- |
| **已花**   | 已经付给供应商，永远留在原项目的账上           |
| **已预占** | 已锁定为某个供应商的付款承诺，到期前谁也挪不走 |
| **可用**   | 只有这部分能被花掉或调拨                       |

四条规则，全部写在合约里：

- **锁款即承诺**：Agent 锁定一笔上限，绑定**指定供应商、订单号和截止时间**。供应商在链上看到承诺就可以开工。
- **供应商独立兑现**：截止前**只有指定供应商**能按实际用量结算，不超过上限、只能结算一次。剩下的钱**在同一笔交易里**回到项目。Agent 掉线也不影响供应商收款。
- **谁也取消不了**：承诺到期前，Agent 和财务都不能取消；财务调拨**只能动“可用”**。
- **并发按链上顺序判定，拒绝也上链**：两笔操作抢同一份钱，先上链的成功，后上链的被拒。被拒的操作不 revert，而是带原因写进链上记录（“承诺还没到期，谁也取消不了”“这笔钱已被预占”“可用余额不足”），供应商和审计方自己就能查。

## 三、现场演示（控制台“一键演示”，四幕九步，约 65 秒，全部是真实交易）

| 幕   | 发生了什么                                                                                           | 合约的反应                                                             |
| ---- | ---------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 准备 | 团队预算 0.1 MON：客服项目（甲）0.06、数据项目（乙）0.04；乙花完，甲只剩 0.02                        |                                                                        |
| 一   | 客服 Agent 锁款 0.02（绑定供应商、订单号、10 分钟截止）→ **Agent 掉线** → 财务想取消承诺、把钱调给乙 | ⛔ 两次都被拦：“承诺还没到期，谁也取消不了”“这笔钱已被预占”            |
| 二   | **供应商用自己的钱包**按实际用量结算 0.012 → 财务调走剩下的 0.008                                    | ✅ 供应商到账；0.008 同一笔交易里回到甲，再被调给乙；已花的留在甲      |
| 三   | Agent 付款 0.02 和财务调拨 0.02 **同时发出**                                                         | 先上链的成功，另一笔被拒，账一分不差                                   |
| 四   | 项目只剩 0.03，**20 个 Agent 同时**各付 0.0025                                                       | ✅ 成功 12 笔、⛔ 被拒 8 笔（可用余额不足），总支出正好 0.03，一分不超 |

每一步的交易都能点开，在区块浏览器里核对区块号和区块内序号。

### 测试网实测（2026-11-21）

- 供应商结算 0.012 和剩余 0.008 释放，发生在**同一个区块 81517447**。
- 幕三两笔交易落在**同一个区块 81517517**：Agent 付款成功，财务调拨被拒（可用余额不足）。两种先后顺序都实测过，结果都正确。
- 幕四 20 笔并发付款落在区块 81523842–81523849（约 2.4 秒）：成功 12 笔、被拒 8 笔，项目可用余额归零，总支出 = 预算 0.03。

## 四、为什么必须在链上，为什么是 Monad

- **账本必须谁都改不了**：财务、Agent、供应商三方都绕不过合约。供应商不需要信任 Agent 或平台的服务器，看到链上承诺就能开工；被拒的操作带原因留在链上，第三方自己就能查。
- **Agent 的支付是高频小额**：Agent 每调用一次服务就锁一次款、结一次账，需要亚秒确认和极低手续费。Monad 300ms 出块，20 个 Agent 同时付款约 2.4 秒全部上链，控制台上的预算几乎实时更新。

## 五、和已有方案的区别

| 项目                                 | 做了什么                                       | 区别                                                                       |
| ------------------------------------ | ---------------------------------------------- | -------------------------------------------------------------------------- |
| SDWallet（Monad Blitz 杭州 V2 冠军） | 单个 Agent 的单笔 / 每日限额、收款白名单、x402 | 只有一个资金池，没有项目层、调拨和供应商承诺                               |
| SmartBudget（杭州 V2）               | 单笔 / 每日 / 每周限额                         | 预算仍是一个池子，财务挪不走，也不能占住正在花的钱                         |
| x402 `upto` 方案                     | 先授权上限、再按实际用量结算                   | 是单次支付层面的预授权；没有项目预算、财务调拨和“到期前谁也取消不了”的承诺 |
| TaskPay、Bursar、OpenAgentPay        | 任务预算、拒付事件、链下分级预算               | 没有把供应商收款承诺和项目间调拨放进同一个链上账本                         |

**Encumber 的切入点：供应商的收款承诺和财务的预算调拨，由同一个项目金库强制执行。**

## 六、谁会用、怎么收费

- 帮多个客户运行 AI Agent 的自动化服务商：每个客户、每个项目的钱必须分得清。
- 按量计费的大模型、数据、算力供应商：凭链上承诺决定是否开工，不怕坏账。
- 收费设想：按团队收控制台订阅费；按结算笔数收少量服务费（待验证）。
